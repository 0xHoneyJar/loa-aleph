I clarify the adopted F-03 accepted-worker-return production-reachability design for cumulative run format 1.9.0-provisional and capability orchestrator-work-transitions as follows.

A valid S3 normalizer `widen_requests` request that states that an original claim candidate cannot be faithfully normalized or affirmatively admitted without additional exact source context is a retained repair obligation. It MUST NOT be discarded, treated as already-satisfied merely because the context was visible for inspection, or bypassed by admitting the original claim against unpacketed text.

For new cumulative `1.9.0-provisional` runs using `orchestrator-work-transitions`, Core shall provide a dedicated, bounded post-S2 packet-widening work family executed while the run remains in S3.

This work family does NOT reopen S2.

It does NOT invalidate, delete, replace, or regenerate the existing S2 stage seal.

It does NOT permit new general S2 extraction work after S2 closure.

It exists only to satisfy an authenticated S3 packet-widening obligation already emitted by a valid normalizer return under the existing Core contract.

## Trigger and original claim candidate

The triggering S3 normalizer return remains immutable.

Its original `claim-candidate:<index>` selector remains retained.

A widening request blocks affirmative admission of that claim candidate until the widening obligation has either:

- completed successfully and all subsequently required fresh review/admission predicates are satisfied; or
- reached an existing valid nonaffirmative/unresolved outcome.

Core MUST NOT silently remove the widening request from the candidate.

Core MUST NOT treat bounded inspection context as packet evidence.

Core MUST NOT rewrite the original normalizer return to pretend the wider PKT already existed.

## Bounded widening work

Core shall derive a dedicated work item from the exact validated widening request.

The work identity MUST bind at minimum:

- run and pinned run format/capability;
- current S3 stage and checkpoint;
- original normalizer invocation;
- original `claim-candidate:<index>`;
- exact widening-request entry;
- requested source;
- requested locator or exact widening bounds;
- predecessor packet identity or identities where the existing request supplies them;
- frozen source hash;
- current packet and lineage state;
- current chain head;
- intended packet operation family.

The worker, skill, parent model, or adapter may not broaden those bounds.

A widening worker may inspect only the frozen source material mechanically authorized by that exact request and the minimum retained predecessor packet/context required by the Core contract.

## Producer role

The post-S2 widening operation uses a dedicated 1.9 packet-widening producer contract.

It may reuse the existing `extractor` worker role operationally, but only under this explicitly distinct S3 packet-widening contract and work identity.

This is a narrow exception to the ordinary rule that general extractor work belongs to S2.

An S3 packet-widening invocation is NOT permission to:

- restart the primary source walk;
- reconsider extraction criteria;
- search the source generally for additional candidates;
- repair unrelated missed extraction;
- revise S2 gap-review conclusions;
- rewrite prior packets;
- produce claims.

The widening producer's task is limited to the exact source locus requested by the retained S3 widening obligation.

If the requested locus cannot be mechanically reopened from the frozen source under the pinned exact-evidence contract, widening fails closed. It MUST NOT substitute rendered, normalized, remembered, OCR-like, or inferred text.

## New packet identity

A successful widening creates one or more NEW canonical PKT identities as required by the existing packet fragmentation/join rules.

An existing committed PKT is never expanded or rewritten in place.

The original PKT row, exact-evidence record, semantic subject, reviews and receipts remain immutable.

Where the widening has an existing PKT predecessor, the new packet identity MUST be connected through the existing PKT lineage contract using the already-adopted Slice 3 split/replace/supersede semantics appropriate to the mechanically derived predecessor/successor cardinality.

This clarification creates no new lineage type.

If the existing adopted lineage predicates do not mechanically determine a legal lineage treatment for a particular requested widening, implementation MUST stop rather than invent one.

Where an already-existing normalizer contract expressly permits an add-packet request with no packet predecessor, Core may create a new exact PKT bound directly to that exact widening request and frozen source locus only if the existing Core contract already defines that request form. This clarification does not invent a new unbounded add-packet request shape.

## S2 seal and historical state

The existing S2 seal remains an immutable historical statement about the state that satisfied S2 when S2 exited.

Post-S2 widening does not retroactively alter that historical statement.

Accordingly, the widening operation MUST NOT modify or delete:

- S2 primary walk intervals;
- S2 extraction-event rows;
- S2 resume cursors;
- S2 fresh gap-review rows;
- the S2 per-source completion snapshot as historically sealed;
- existing S2 semantic subjects;
- existing S2 L2S assignments/results;
- existing S2 material receipts;
- the S2 semantic stage-seal record.

No generic stage rewind is authorized.

No second S2 exit or replacement S2 seal is created.

## Source-walk accounting

A post-S2 widening is legal only over frozen source bytes whose source identity and byte/locus coverage were already accounted for by the completed S2 source walk.

The requested widened span MUST lie wholly inside the frozen source and wholly inside source coverage already established at S2 closure.

Widening does not convert previously inspected or noncandidate source bytes into evidence merely by reference. Only the newly materialized exact PKT becomes evidence after exact-byte verification and its required review path succeeds.

The historical primary source-walk rows remain unchanged.

The widening transaction MUST retain enough mechanical provenance to prove:

- source ID and frozen source hash;
- exact requested source locus;
- predecessor PKT basis where applicable;
- exact new fragment bytes and hashes;
- widening-request identity;
- new PKT identity;
- lineage treatment where applicable.

Do not manufacture a new primary walk interval, cursor, gap review, or ordinary primary extraction event merely to make the post-S2 packet look as though it was extracted during S2.

If an existing adopted source-walk schema already has an explicit non-primary reconciliation/event form suitable for this operation, it may be used exactly under that existing contract. Otherwise the post-S2 widening provenance belongs to the dedicated work transaction, exact-evidence record and PKT lineage; no new source-walk event schema is invented by implementation.

## Fresh packet semantics

A newly materialized widened PKT does not inherit the predecessor packet's semantic review merely because it overlaps or contains the predecessor bytes.

Different packet bytes require a fresh semantic subject.

The dedicated widening producer MUST return the semantic proposal required by the existing packet semantic contract for every new packet candidate produced by this operation.

The new semantic subject MUST bind the exact new PKT bytes and the exact post-S2 widening producer return.

The predecessor packet's existing semantic subject remains historical and immutable.

The new packet must receive fresh L2S before it may serve as affirmative packet evidence for the triggering S3 claim candidate.

Reusing an old semantic-subject digest, old packet review, or old exact-evidence binding for changed packet bytes is forbidden.

## Semantic owner stage

The new packet semantic subject created by this bounded post-S2 family is owned by S3.

For cumulative 1.9 orchestration runs, a `packet-group` semantic subject MAY therefore have `owner_stage = S3` only when all of the following are true:

- it is generated by the dedicated post-S2 packet-widening work family;
- its work item is bound to a valid retained S3 widening request;
- its new PKT basis is mechanically exact;
- its source is the same frozen source authorized by the request;
- all predecessor/lineage constraints are satisfied;
- the original S2 seal remains unchanged.

This exception does not permit ordinary packet production or arbitrary extractor work in S3.

Ordinary packets produced during primary extraction remain S2-owned.

## Material-use receipt ownership

Canonical representation/material-use rules remain strict.

For a new widened PKT produced by this dedicated family, the canonical PKT material-use receipt and any required L2F work MAY be owned by S3, but only for the packet created by this exact post-S2 widening transaction.

This is a bounded 1.9 exception to ordinary S2 PKT receipt ownership.

It does not permit:

- CC or REL use with `CANNOT_DETERMINE` material;
- invented material availability;
- reuse of a predecessor packet's receipt when the new PKT has a different exact basis;
- arbitrary S3 packet receipts unrelated to an authenticated widening request.

Any required L2F review remains independent of L2S.

## Claim re-evaluation

Successful packet widening does not automatically admit the original claim candidate.

After the new PKT has:

- exact-evidence verification;
- required packet semantic proposal;
- fresh L2S;
- any applicable material review;
- legal lineage/provenance closure;

Core shall derive a new S3 claim-review obligation whose packet basis contains the exact packet identities that are then legally current/applicable under the existing lineage and claim contracts.

The triggering normalizer's original raw bytes remain immutable.

If the original claim candidate cannot legally bind to the resulting packet basis without a producer revision under existing Core semantics, Core MUST request the existing legal revision/successor path rather than silently rewrite that candidate.

No widening operation may itself invent or alter normalized claim text.

## Failure and unresolved behavior

If widening cannot complete because:

- exact source bytes cannot be reopened;
- requested bounds are invalid;
- lineage is illegal;
- the new packet semantic proposal is refuted or unresolved;
- required material use is unavailable;
- the packet cannot satisfy required fresh review;
- the triggering claim still requires unpacketed context afterward;

the original affirmative claim remains blocked.

Core MUST preserve the widening request and failure evidence.

It MUST NOT:

- admit the original claim anyway;
- silently downgrade the request;
- turn inspected text into evidence;
- invent `no-claim`;
- discard the candidate;
- reopen S2 generically.

## Recovery and exactly-once effects

Architecture-B recovery applies to the widening family.

A widening transaction MUST be bound to the durable work identity and must be recoverable from exact before/after evidence.

Repeated resume MUST NOT create:

- multiple successor PKTs for one already-consumed widening work item;
- duplicate exact-evidence records;
- duplicate lineage rows;
- duplicate semantic subjects;
- duplicate material receipts;
- duplicate work consumption.

Unknown worker-dispatch outcome remains a fail-closed halt.

Exactly-once provider execution is not claimed.

Only exactly-once canonical effects may be claimed where demonstrated.
